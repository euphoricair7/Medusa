# Database Schema

Medusa uses PostgreSQL to persist Falco alerts and forensic checkpoint events. Tables are created automatically by the FastAPI application on startup (via SQLAlchemy) and are also defined in [`infra/postgres/init/01_schema.sql`](../../infra/postgres/init/01_schema.sql).

## `alerts`

Stores normalized Falco runtime alerts with the full raw webhook payload for forensic analysis.

| Column | Type | Nullable | Description |
|--------|------|----------|-------------|
| `id` | `UUID` | NO | Primary key. Auto-generated unique identifier for the alert record. |
| `received_at` | `TIMESTAMPTZ` | NO | Timestamp when the Medusa API received and persisted the alert. Defaults to `NOW()`. |
| `rule` | `TEXT` | NO | Name of the Falco rule that triggered the alert (e.g. `Terminal shell in container`). |
| `priority` | `TEXT` | NO | Severity level assigned by Falco (`critical`, `error`, `warning`, `notice`, `info`, `debug`). |
| `output` | `TEXT` | NO | Human-readable alert message generated by Falco from the rule's output template. |
| `container_name` | `TEXT` | YES | Name of the container where the event occurred, extracted from `output_fields.container.name`. |
| `namespace` | `TEXT` | YES | Kubernetes namespace, extracted from `output_fields.k8s.ns.name` (or fallbacks). Populated on Falco ingest when cluster metadata is present. |
| `pod_name` | `TEXT` | YES | Kubernetes pod name, extracted from `output_fields.k8s.pod.name` (or fallbacks). Required for automatic forensic triggering. |
| `image` | `TEXT` | YES | Container image repository, extracted from `output_fields.container.image.repository`. |
| `tags` | `TEXT[]` | YES | Tags associated with the triggered Falco rule (e.g. MITRE technique identifiers). |
| `raw_event` | `JSONB` | NO | Full payload for replay. Falco alerts store the webhook JSON; manual alerts store the request with `"source": "manual"`. |

## `forensic_events`

Tracks forensic checkpoint jobs from initial alert reception through CRIU snapshot capture.

| Column | Type | Nullable | Description |
|--------|------|----------|-------------|
| `id` | `UUID` | NO | Primary key. Auto-generated unique identifier for the forensic event. |
| `created_at` | `TIMESTAMPTZ` | NO | Timestamp when the forensic event was first created. Defaults to `NOW()`. |
| `updated_at` | `TIMESTAMPTZ` | YES | Timestamp of the most recent update to the event (e.g. phase transition). |
| `alert_id` | `UUID` | YES | Foreign key referencing `alerts.id`. Links this checkpoint job to the originating Falco alert, when known. |
| `pod_name` | `TEXT` | YES | Kubernetes pod hosting the target container. Populated for manual triggers or by the checkpoint pipeline. |
| `namespace` | `TEXT` | YES | Kubernetes namespace of the target pod. |
| `container_name` | `TEXT` | YES | Specific container within the pod targeted for CRIU checkpointing. |
| `phase` | `TEXT` | NO | Current lifecycle state of the checkpoint job. Defaults to `pending`. See [API overview](../api/overview.md#forensic-event-lifecycle) for valid values. |
| `trigger_source` | `TEXT` | YES | How the event was created. `manual` for **POST `/alerts/manual`**; `falco` for Medusa-tagged alerts ingested via **POST `/alerts/falco`**. |
| `triggered_rule` | `TEXT` | YES | Falco rule name that triggered the event (populated for Falco-sourced events). |
| `triggered_priority` | `TEXT` | YES | Priority of the triggering alert at creation time. |
| `checkpoint_location` | `TEXT` | YES | Storage path or URI where the CRIU memory snapshot artifact is stored after a successful checkpoint. |
| `raw_alert` | `JSONB` | YES | Original alert payload associated with this event (typically the Falco webhook JSON). |
| `raw_report` | `JSONB` | YES | Merged forensic payload. Nested keys: `operator` (sync), `checkpointctl` (analysis API), optional `error` (CR create failures). See [raw_report shape](#raw_report-shape). |
| `idempotency_key` | `TEXT` | YES | SHA-256 of `{alert_id}:{namespace}:{pod_name}:{container_name}`. One forensic event per alert; duplicate submits reuse the row. |
| `operator_cr_name` | `TEXT` | YES | Name of the `ForensicSnapshotChain` CR in Kubernetes. |

### `raw_report` shape

One JSONB column holds capture status and (later) checkpointctl analysis without writers clobbering each other:

| Key | Writer | Content |
| --- | ------ | ------- |
| `operator` | `forensic_sync` CR poll | Operator phase, `snapshot_chain_records`, conditions, optional signed manifest fields |
| `checkpointctl` | **POST** `/forensic-checkpoint/{event_id}/analysis` | `checkpoint_path`, `node_name`, `analyzer`, `analyzed_at`, `report` |
| `error` | `forensic_service` on CR create failure | `{"cr_create_error": "..."}`; removed when CR create succeeds on retry |

Sync assigns only `raw_report["operator"]`. The analysis endpoint assigns only `raw_report["checkpointctl"]`. See [API overview](../api/overview.md#raw_report-shape).

## Indexes

Defined in [`01_schema.sql`](../../infra/postgres/init/01_schema.sql):

| Index | Table | Purpose |
| ----- | ----- | ------- |
| `idx_alerts_received_at` | `alerts` | Time-range listing (`GET /alerts/`, newest first) |
| `idx_alerts_priority` | `alerts` | Severity filtering |
| `idx_alerts_container` | `alerts` | Container-scoped lookups |
| `idx_alerts_namespace` | `alerts` | Namespace filtering |
| `idx_alerts_pod_name` | `alerts` | Pod-scoped lookups |
| `idempotency_key` (UNIQUE) | `forensic_events` | Alert-scoped dedup in `process_trigger_forensic` |

No other indexes on `forensic_events` yet. Add them if query patterns require (e.g. filtering by `phase`).

## Relationships

### `alerts` → `forensic_events`

A single Falco alert may spawn zero or more forensic checkpoint events. The relationship is optional on both sides:

- **`forensic_events.alert_id`** is a nullable foreign key to **`alerts.id`**.
- When `alert_id` is set, the forensic event is explicitly linked to a persisted alert record.
- When `alert_id` is `NULL`, the forensic event has no linked alert row.

**Manual flow:** **POST `/alerts/manual`** creates a new alert when `alert_id` is omitted, or links an existing alert when supplied.

**Automatic flow:** **POST `/alerts/falco`** always persists the alert. Forensic triggering runs only when the Falco rule includes the `medusa` tag, priority meets `MIN_ALERT_PRIORITY` (default `warning`), and `k8s.pod.name` is present in `output_fields`. Ingestion succeeds even if forensic triggering fails.

**Pod dedup:** When multiple alerts arrive for the same pod while a capture is `queued` or `in_progress`, later alerts reuse the active `forensic_events` row (no second CR). Each alert still gets its own `alerts` row.

**Idempotency:** The shared trigger hashes `alert_id`, namespace, pod, and container into `idempotency_key`. A second request for the same alert returns the existing row when the operator CR is present and phase is `queued`, `in_progress`, or `success`. If the CR was deleted or phase is `failed`, the API recreates the CR on the same row and clears stale `checkpoint_location`.

See [`er-diagram.md`](er-diagram.md) for a visual representation of this relationship.
